# LensLabs product plan

Date: **2026-09-04**. **R1 is a bounded local beta with verified small-project browser workflows and controlled storage-failure checks.** See the [release evidence and limits](RELEASE-1.md). This plan separates existing bounded behavior, proposed architecture, release targets and external dependencies; it does not claim a complete platform or authorize publishing, account changes, outgoing messages or spending.

## Thesis and customer assumptions

LensLabs should connect inquiry, assignment, images, creative decisions, client feedback, delivery, payment and later retrieval through the same project and asset identities. Its value is fewer repeated uploads, duplicate client records, lost approvals and manual handoffs—not thirteen unrelated tools behind one login.

Sports and high-volume events are the initial **customer hypothesis**, not a proven market. A press-box photographer needs a useful first delivery while the rest of a 3,000+ image assignment continues processing. That makes ingest recovery, camera identity, deadline coverage, reversible decisions and understandable editing especially important. Portraits, weddings, commercial/product/property work, volume picture days and personal projects should use the same model with different templates.

Do not claim that all-in-one photography software is new. The [competitive research](COMPETITIVE-RESEARCH.md) records dated official capabilities from Pixieset, Photo Mechanic, Adobe, Capture One, HoneyBook, Pic-Time, PhotoShelter and PhotoDay. Our differentiation remains to be demonstrated through complete assignments, correction effort, trustworthy handoffs and actual subscriptions retired.

## Scope and honest capability states

- **Working, bounded:** demonstrated behavior on named formats, environments and workflows; attach test evidence and limitations.
- **Partial:** useful behavior exists, but a complete replacement acceptance test does not pass.
- **Integration requiring configuration:** depends on another service/tool, authorized credentials and end-to-end verification. Its external subscription remains a cost.
- **Experimental:** a measurable baseline or model under evaluation, not a reliable product promise.
- **Planned:** no supported completion path yet.
- **Release candidate:** code is being assembled; no new completion claim until verification results are recorded.

The existing plain-English planner handles a finite supported set of reversible whole-image adjustments; it is not an open-ended visual agent. Baseline image-wide analysis is not sports understanding. Quality is defined by the concrete acceptance scenarios below, not an arbitrary percentage or an AGI/product-completeness score. A useful image must remain reachable even when a model is uncertain or processing fails.

## Shared project and asset model

The implemented `src/lib/projects/model.ts` defines a device-local versioned project with optional client/booking/gallery/invoice links, frames, original/preview blob references, edit versions, decisions, activity, proofs, feedback and export records. Checksums are fingerprints of bytes; the schema distinguishes checksum-backed source identity from explicitly unverified source references. Its local owner identifiers are placeholders for the single-user boundary, **not authentication or tenant isolation**.

Proof items reference the exact frame, asset, edit version and rendered blob. Feedback references that proof/version and records that the photographer entered it. An export marked `download-prepared` is not proof of transfer or client receipt. These distinctions remain visible in the local UI and are covered by R1 verification. Business links carry explicit IDs and reference snapshots; project restore does not import or replace live CRM, booking, payment or gallery records.

The full shared domain expands without creating incompatible genre-specific records:

| Domain | Connected entities and invariants |
| --- | --- |
| People and access | Organizations, members, roles, clients, subjects, teams, roster versions and project access grants. A client/customer is not automatically a photographed subject. Recognition never grants access. |
| Assignment | Projects, sessions, locations, briefs, requirements/shot lists, priority subjects, deadlines, deliverables, team tasks, booking and document references. Personal/editorial projects can start without a client or payment. |
| Image identity | Original captures, RAW/JPEG representations, source locations, verified byte blobs, derivatives, collections, metadata and edit versions. Reusing a capture does not create unrelated originals; visually similar photographs are not byte duplicates. RAW/JPEG pairing remains a tested future relationship, not inferred from basename alone. |
| Creative decisions | Machine assessments/proposals, human selections/protection, burst groups, edits and version history. Preserve actor, time, inputs, processor/model version and reversible actions. Keep uncertain recommendations separate from approvals. |
| Review and distribution | Proof sets, exact-version favorites/comments/revision requests/approvals, galleries, grants, publications, export jobs, delivery manifests and receipts. An edit after approval creates a new version and cannot silently replace the delivered one. |
| Business | Inquiries, quotes/proposals, packages, questionnaires, documents/signatures, booking holds, invoices, payments, credits/refunds, expenses, orders and fulfillment. Booked value, invoiced value and cash collected are separate. |
| Operations | Automations/runs, processing jobs, provider events/outbox, sync operations/conflicts, indexes, backup manifests, restores, usage/entitlements and activity history. Preserve provider/import identifiers and audit relationships. |

Selection, editing, client approval, publication, payment and backup each have independent state. A favorite need not be a keeper; publication need not be final approval; payment need not complete every obligation. App-generated IDs remain stable during migration, while imported/provider IDs are retained in separate source mappings.

Genre templates configure terminology/defaults, not separate databases. Sports preparation retains camera time, real-world time and displayed game clock separately with offsets/uncertainty. Weddings/group portraits track required people and meaningful expressions. Panorama, bracketed-exposure and focus-stack source sequences remain intact. Product/property work carries usage/release and output requirements; volume/youth work needs scoped subject galleries and non-biometric access alternatives. Required delivery counts must be labeled as contractual requirements versus targets, with visible shortfalls.

## Architecture decisions

1. **Keep the repository's stack:** React + TanStack Start/file routes, current visual system and Supabase-backed server boundaries. Begin as a modular application, not a rewrite or premature service split. Keep the existing Lovable layout during current implementation; a compact Home/Projects/Library/Clients/Calendar/Business/Settings navigation is a later, explicitly reviewed migration, not an incidental redesign.
2. **Browser-first, bounded local workspace:** workers handle analysis away from interactive rendering; IndexedDB stores durable local records/blobs where supported. Use bounded concurrency, backpressure, cancellation, progress and source reconnect. Check capacity before copying originals; never describe preview caching as verified original backup.
3. **Shared domain, separate storage:** metadata/relationships, original bytes, derivatives, jobs, indexes and backups have distinct ownership/lifecycles. Validate complete snapshots and relationships; fail closed on unreadable state. Use revision checks, safe transactions and immutable history instead of last-writer-wins overwrites.
4. **Web business/client plane:** server-authorized organization/project queries and short-lived file grants. Public portfolios, guest proofs, authenticated clients and internal/team views are distinct. Authorization applies to thumbnails, originals, downloads, search representations and jobs—not just route visibility. Secrets stay server-side; logs are redacted.
5. **Native image boundary:** add a tested desktop processing/drive adapter for dependable heavy RAW, long-running ingest, offline storage, watched folders and eventual supported tethering. Importing another app's tethered output is not direct camera control. Camera support, OS permissions, reconnects and the RAW renderer each require fixtures.
6. **Provider adapters:** rendering, identity/OCR, language/vision models, payments, signatures, calendars, email and labs expose typed inputs, jobs, cost estimates and verifiable results. No success before application/provider confirmation. Refer to [provider boundaries](PROVIDER-BOUNDARIES.md) for rights, Stripe, LibRaw, browser, metadata, accessibility and cost gates.
7. **Offline and synchronization:** queue authorized local changes with their base revision; preserve human decisions and show conflicts. Apply revocations on reconnect and explain offline limitations. Backups have independent retention and restoration; synchronization that propagates deletion is not a backup strategy.

Personalized editing or model-improvement use requires separate explicit permission for the examples, originals, identities and preferences involved; upload is not training consent. Future masks/annotations must transform correctly with orientation/crop, and view zoom remains distinct from crop. Bookkeeping exports, receipts and cost estimates are useful business scope; banking, comprehensive accounting and tax filing are not claimed replacements.

## Key user flows

- **First useful task:** ask solo/team, genres, present workflow/tools and storage preference only when these change the experience. Allow **Import photos now** without business setup or a client. Show supported formats and source/storage state.
- **Deadline-first assignment:** project brief/roster/requirements → multi-camera ingest while browsing → protect/select useful frames → review plain-English edit proposal → apply to explicit lighting/selection scope → prepare a small first proof/export → continue the rest of the assignment. Show missing required subjects and outputs rather than a misleading “done” score.
- **Client-led assignment:** site inquiry → scoped lead/client → quote/questionnaire/document → available-slot hold → confirmed booking → shared project/brief → shoot/review → exact-version client proof → revisions/final approval → delivery → invoice/payment reconciliation. Avoid re-entering identities at handoffs.
- **Personal/editorial:** direct ingest → nondestructive edit/version → metadata/licensing/credit checks → appropriate output recipe/agency submission → archive. Generation can be disabled; no invented athlete/event facts enter editorial captions.
- **Recover or migrate:** supported folder/metadata/client/provider export → preview mappings/duplicates/conflicts/unsupported fields → resumable idempotent import → reconciliation report → reopen and verify originals/relationships. Export supported recipes, originals and manifests; preserve unsupported fields without claiming to interpret them.
- **Review on a phone:** authorized client sees only intended next actions, usable image size and simple favorites/comments/approval. Preserve the exact reviewed version. Download resolution, expiry and revocation limits are clear; disabled buttons/watermarks do not prevent screenshots or retrieve prior copies.

Re-read current state before reminders and stop satisfied work. A booking-to-project rule can precede an email or paid-order rule; enabling one does not authorize the others.

## Quality gates and pilot plan

### Hard safety gates

No known source loss, silent cross-user overwrite, unauthorized file access, double financial posting or unapproved external side effect is acceptable. An unsupported file or model assessment must remain an explicit recoverable issue. Use real permitted fixtures alongside synthetic stress tests; duplicated tiny JPEGs do not validate sports selection or full-resolution RAW throughput.

Required scenarios include: two cameras sharing filenames; interrupted ingest/resume; athlete blur against sharp background; protected intentional-motion/closed-eye frames; burst/identity correction without unrelated changes; edit/export/reopen fidelity; feedback bound to the correct version; unauthorized original access; retry-safe provider events; payment while a reminder waits; visible offline edit conflict; and backup restoration/migration. Record hardware, OS/browser, camera/format/dimensions, network, cache and model settings with measured timings.

Web accessibility targets **WCAG 2.2 AA**, with manual keyboard/screen-reader/mobile checks and automated checks on complete supported flows. The target is not a compliance claim. Test focus/scroll retention during virtualization and background updates, non-color state cues, discoverable/remappable shortcuts, reduced motion and non-drag alternatives.

### Customer research — proposed, not conducted

Recruit an initial six-to-eight-person pilot spanning deadline-driven sports, high-volume events and at least one portrait/small-studio workflow. Interview around the last real paid assignment, actual tools/bills, feared losses, handoffs and reasons not to switch. Obtain permission for fixtures; observe the existing workflow before showing ours. Do not fabricate interviews, demand or testimonials.

Use paired assignments or suitably matched permitted sets to reduce learning/order bias. Ask photographers to identify multiple acceptable frames and required moments; inspect what the system suggested rejecting. Keep training and evaluation events separate. Repeat over several assignments before claiming durable usefulness.

| Hypothesis | Pilot evidence / provisional decision rule |
| --- | --- |
| Fast first delivery is a stronger wedge than generic all-in-one | Time to first useful preview, first approved batch and delivered deadline set; capture where waiting/correction occurs. Continue sports-first only if real users repeatedly value the advantage. |
| Plain English reduces work without removing creative control | Request-to-approved-result time, clarification rate, wrong-scope proposals, accept/undo and manual correction effort; always expose affected images. |
| Connected records reduce administration | Re-entry count, incorrect links and handoff time across inquiry/booking/project/proof/invoice; target zero required re-entry of already known identity fields in the supported path. |
| Photographers can complete the release independently | Observe the concrete supported acceptance scenarios, record assistance, failures and recovery, and report the sample size. Establish task-specific thresholds with photographers using labeled real shoots; do not substitute an arbitrary completion percentage for workflow evidence. |
| Consolidation is real and economically viable | Record actual tools retired only after their category gates, repeat use, willingness to pay, support minutes, delivery success and measured variable costs. Paid integrations remain on the bill. |

Keeper recall (valuable images retained), selection precision (suggested images judged useful), subject/moment coverage and correction time are reported separately. Agree assignment-specific tolerances before testing; losing one mandatory frame can fail a shoot despite a high average score. Set provisional latency/cost budgets before optimization and publish observed results without converting targets into claims.

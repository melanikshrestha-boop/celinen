## Precision and color boundaries

- **8-bit input/output bottleneck:** LibRaw is configured with `output_bps=8`; ImageIO draws raster input into an 8-bit sRGB context. Native adjustments use floating-point working values after that conversion, then quantize back to RGBA8 before JPEG encoding. Float arithmetic does not recover precision, gamut or highlight data already lost at the 8-bit conversion. Transparency is composited onto white for the JPEG path.
- **Relative RAW WB, not calibrated temperature:** the RAW path uses camera/daylight multipliers before demosaic; the raster/preview path applies relative encoded-RGB gains. They are not interchangeable Kelvin controls. No neutral-target eyedropper or measured camera-profile workflow is implemented. Adobe's [white-balance documentation](https://helpx.adobe.com/lightroom-classic/desktop/process-and-develop-photos/image-tone-color.html) distinguishes neutral sampling and RAW temperature from non-RAW relative adjustment.
- **Known missing-camera-WB discontinuity, not fixed:** when usable camera WB is absent, zero Temp/Tint can use LibRaw's automatic fallback while a nonzero relative adjustment switches to the daylight `pre_mul` baseline. A generated 128×96 DNG without AsShotNeutral reproduced a mean absolute change of about 3.82 / 255, maximum 38, for a ±0.000001 adjustment; a control with camera WB did not jump. This is one synthetic diagnostic, not evidence of failure in all Sony files. Correcting it needs explicit rendering compatibility and continuity tests before reinterpreting existing recipes. `native/src/develop_raw.cpp` also configures camera-matrix options after `open_buffer`; affected non-DNG matrix selection still needs a representative camera fixture before a fidelity claim.
- **Profiles and soft proof are still absent:** sRGB conversion/tagging is not calibrated camera rendering, a wide-gamut editing pipeline, printer ICC simulation, rendering-intent selection or gamut checking. Export preview means the exact downloadable JPEG, not print soft proof. Display/application differences outside this tested path are not controlled here.
- **Highlight limits:** Highlights/Whites, film falloff and exposure manipulate available rendered values. They do not promise sensor highlight reconstruction, unclipped HDR working values or Adobe-equivalent recovery. A future high-bit pipeline needs gradient/clipping/profile-chart tests and versioned recipe behavior, not just a 16-bit file wrapper.

The native recipe math and source mode are separate from UI labels. The [Adobe grading explanation](https://blog.adobe.com/en/publish/2020/10/20/introducing-color-grading) is a workflow reference, not an implementation specification or output certification.

## Cause and correction

The RAW editor previously applied edits to a cached camera-preview JPEG at a 1,600-pixel long edge, while the default export demosaiced the original sensor RAW at a 4,096-pixel bound. Camera tone processing and white balance differ from LibRaw's sensor rendering; exposure and white-balance edits also entered these two paths at different stages. Both JPEG paths were tagged sRGB. The reproduced mismatch was not an unverified color-profile guess.

On the public Sony A7 IV fixture, the same edited recipe produced normalized mean display luminance **0.564614** through the old camera-preview path versus **0.407675** through the sensor path at 1,600 pixels. The sensor export at its available 3,516 × 2,344 resolution measured **0.407549**. This isolates the dominant difference to the input/rendering path, not export resolution.

The editor now resolves processing source, source mode, export edge and JPEG quality together:

- Available RAW defaults to the original sensor RAW for both editing and export. Explicit saved-preview mode changes both; a failed sensor decode does not silently fall back.
- Before/after and source statistics use the same selected processing mode. A completed ordinary edited view uses the same size, quality and recipe as export; geometry tools intentionally display their uncropped editing coordinate space. While preparing that frame, a cached image may appear explicitly as **Import preview**. It is never an export proof or a source-coordinate editing surface.
- A completed edited JPEG is reused for export only when photo identity, source Blob identity, full recipe, source mode, edge and quality all match. A changed source/mode/size invalidates old-frame ownership; aborted work cannot publish a stale result.
- RAW neutral and edited jobs are sequenced through the bounded worker lane. Neutral recipes reuse their completed JPEG. Expensive full-resolution rendering is debounced, not represented as an instant low-resolution substitute.
- Original files, existing saved recipes and camera thumbnails are not rewritten or migrated. Preview-only records remain explicitly preview-only.

LibRaw still renders into an 8-bit sRGB working image before the remaining C++ operations. Input limits remain 128 MiB / 60 million sensor pixels. The current JPEG default remains 4,096 pixels; the new explicit larger option is bounded by both an 8,192-pixel edge and 36 million output pixels, without upscaling. This is not a high-bit-depth Adobe pipeline, an unlimited original-resolution export, a promise of clipped-highlight recovery, or identical appearance in every external display/application.

## Object removal: experimental, local, separate copy

Object selection uses the public **macOS 14+ Vision foreground-instance API** through the local native engine. It is not available merely because a hosted web page loads, and device/runtime failures must remain visible. Selection analysis is bounded to 1,600 pixels; the returned mask is mapped into a separate removal render capped at 4,096 pixels, independently of the larger export setting. Nearby people may share a detected instance, and arbitrary background objects may not be detected.

The reconstruction is deterministic **C++ exemplar texture fill**, not a trained generative inpainting model. It copies available surrounding texture into the selected mask; it cannot infer reliable unseen people, fences or scene geometry. Input masks are bounded to at most half the image, with a small edge margin. The native fill preserves every unselected RGBA byte and leaves its input arrays unchanged. The transport accepts pixels, not client filesystem paths; requests require the loopback/origin/session guards and have byte, worker and time limits.

The user reviews Before/After and explicitly chooses **Save Copy**. This creates a separate, baked PNG from the selected processing source and recipe rendered up to 4,096 pixels; the editor's export-size preference remains unchanged. It is not a new editable RAW or a non-destructive removal mask inside the original recipe. The original photo and its history remain available and unchanged. PNG encoding is lossless, but its input is the already-rendered JPEG, so it does not restore RAW detail or undo JPEG losses.
